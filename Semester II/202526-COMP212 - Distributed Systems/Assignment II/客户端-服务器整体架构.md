# 客户端-服务器整体架构

对于 `Client` 和 `Server`而言，他们共有的资源是`CastVote`接口，该接口规范了 `Server` 端能提供的服务。 但是对于 `CastVote`接口的实现类， `Client` 端是**不可见的**。因此，对于分布式的 `Client` 端而言，他们无需关心实现类的具体细节，而只需要通过RMI注册即可访问此服务。具体说明如下。

## 服务器

对于 `Server` 而言，一共有两个方法，分别是`run()`方法和`terminate()`方法。

`run()`方法的主要目的是启动 `Server` ，通过实例化`CastVote`接口（也就是通过泛型的方法，创建出 `CastVoteImpl`对象）来承担运算的主要责任。同时， `Server` 会先通过通过`Registry`绑定端口（1099），随后向`register`绑定RMI 服务名称和接口实现类对象。这样`run()`方法就相当于向本地注册了一个RMI方法。`Client`只需要连接到 Server 的地址和对应端口即可使用服务。

`terminate()`方法则是主要做了三件事：从注册表中解绑服务名称、强行释放注册表端口 (1099)、以及释放远程对象。



总体来看，`Server` 中并没有处理逻辑的核心方法，它只负责注册RMI，相当于软件开发中的**Controller**层，真正的请求在`CastVoteImpl`，也就是 逻辑方法被抽离写到了`CastVoteImpl`中，这有助于后期维护和低耦合。



## 客户端

Client 中，有5个 **public** 的方法和2个 **private** 方法。

首先，当 `Client` 对象被创建时，会按顺序调用`registry()`和`connect()`。

`registry()`方法会索取远程 `Server` 的 **registry** 对象，随后 `connect()` 方法会在这个**registry**对象中寻找对应RMI 服务名称的方法，并且强制转换为`CastVote`类型，并赋予给成员变量。这两个方法一旦遇到异常，例如连接异常和类型转换异常（通常是空指针异常，例如虽然连接到服务器，但是并没有找到`CastVote`方法），则会直接抛出对应的异常。 那么 `Client` 就无法完成实例化。 这样设计能够保证，一旦 `Client` 实例被创建出来，则一定可以使用RMI。

`Client`获取ticket使用`getTicket()`方法，获取一个合法的`int`类型的票据。

投票使用`vote()`方法，可能抛出异常（票据不合法等）

获取结果使用`fetchVotingResults()`方法，可能会抛出拒绝访问的异常（例如未投票，但是调用此方法，服务器会拒绝访问）

以及一个额外的方法`getCandidateList()`，如果服务器增加了一些候选人，调用此方法可以更新候选人列表。

这些方法具体实现细节在`CastVoteImpl`中。



# CastVoteImpl部分

## 代码核心介绍

核心部分是`CastVoteImpl`，其承担了分布式访问中的全部细节和处理过程。在本类中除了基本的逻辑，还有不同力度锁的并发控制以满足高并发场景。

`CastVoteImpl`一共有4个成员变量，分别是

1. `validTickets`，**HashSet**，储存那些有效的、未投票的票据。
2. `votedTickets`，**HashSet**，储存那些已经投票过的票据。
3. `votingMap`，**HashMap**，key是候选人的 ID，value是候选人的得票数。
4. `random`，用于随机分发**int**型票据的随机器，**成一个随机的整数凭证**。
5. `lock`，**ReadWriteLock**，可以使用读、写两种不同的锁力度以更好控制高并发。该锁保护的对象是两个Set以及一个Map。**防止在更新投票计数时出现竞态条件**。即使在许多客户端同时投票的情况下，也可以确保投票总数保持准确。



这里用到的数据结构是基于 Hash 的 Set 和 Map， 之所以这么选择，是因为即便在票数非常多的情况下，每次查询仍接近 $O(1)$ 的时间复杂度。

`CastVoteImpl`的构造方法主要是初始化这两个Set和这个Map，并且向Map中预先填充所有的候选人。



`getTicket()`方法会先使用`random`生成一个随机**int**型整数作为ticket。**只要客户端调用远程方法，就验证该凭证。**该方法首先检查这个ticket是否之前被生成出来过（虽然这个概率很低，但是检查是有必要的）。检查方法是从`validTickets`和`votedTickets`这两个HashSet中查找是否存在相同的票据。如果有，那么重新使用`random`生成，直到找到一个合法票据，将凭证存储在HashSet的数据结构中，然后返回。该方法调用前会先抢占写锁。完成后（使用`finally`关键字保证一定释放锁，下同）会释放该锁。在此期间，其他所有的方法涉及到操作、访问Set和Map的操作都会被阻塞，这样能够确保数据修改和读取的一致性和事务的原子性。



`vote()`方法用于投票。方法开始时会抢占写锁，需要传入`ticket`和`choice`两个参数，分别代表`Client`的票据和选择。 本方法首先会确保这个`ticket`存在于`validTickets`集合中，否则直接抛出异常！然后再确保这个`choice`是合法的候选人，如果 Client 试图投票给不存在的候选人，那么本方法会直接返回抛出异常，具体逻辑是使用`votingMap.containsKey(choice)`是否存在该候选人。最后，能确保 `ticket` 和 `choice` 都合法下，会执行操作：先从`validTickets`中删除这个`ticket`，再将这个`ticket`加入`votedTickets`中。最后给对应候选人添加一票（使用`votingMap.merge(choice, 1, Integer::sum)`）方法，这样就可以**维护每个投票选项的计数**，**并且在收到投票时更新计数**。该方法结束后会释放写锁，保证无死锁情况。



`getVotingResults()` 方法则要求传入ticket，此处只抢占读锁。接下来，如果发现该票据不属于`votedTickets`（包括假票、未投票）那么则抛出异常拒绝访问。否则，返回一个**复制后的**新的`return new HashMap<>(votingMap)`（否则可能导致private访问），这样就可以**将当前的投票结果返回给客户端**。



**ReadWriteLock** 可以处理高并发的访问，能保证线程安全，保证Set和Map这些本身不支持并发的数据结构支持并发操作，可以确保不会丢失任何选票，也不会被错误计算。

# Concurrency Test

`ConcurrencyTest`是一个高并发测试类，其步骤如下。

主线程启动 RMI 服务端，并强行休眠 5 秒（`Thread.sleep(5000)`），这是为了确保 RMI 注册表和端口完全绑定就绪，防止客户端连接时发生“连接被拒绝”的错误。

**CountDownLatch**机制：如果用 `for` 循环启动 1000 个线程，由于 CPU 调度的原因，它们其实是“陆陆续续”执行的，算不上真正的极高并发。为了解决这个问题，我们采用了**CountDownLatch**机制来处理1000个 Client 并发：

- 代码中使用了 `CountDownLatch startGate = new CountDownLatch(1);` 作为“发令枪”。
- 1000 个线程启动后，都会阻塞在 `startGate.await();` 起跑线上。
- 主线程准备就绪后，执行 `startGate.countDown();`，**1000 个线程在同一纳秒级瞬间被唤醒，并发向服务器同时发起请求**。这构造了极端的并发竞争条件。

- 每个线程独立创建 `Client`，获取选票（`getTicket()`），并全部投给 `候选人 1`（`vote(1)`）。
  - 无论成功或抛出异常，都会执行 `endGate.countDown();`。主线程通过 `endGate.await();` 阻塞，直到 1000 个线程全部跑完，才会继续往下走，确保测试结果的准确性。

闭环验证 (Mathematical Verification)：

- 主线程最后化身为第 1001 个客户端（`checker`），获取票据并再次投给 `候选人 1`。
- 取回最终结果：拉取服务端返回的哈希表 `results`。
- **断言逻辑**：如果服务端 `Option 1` 的总票数严格等于 `successCount.get() + 1`，则证明在 1000 个并发写操作中，**没有任何一次计票被覆盖或丢失**，完美验证了服务端的线程安全性。

# Access Control Test

这个 `AccessControlTest.java` 是一个自动化测试脚本，专门用于验证服务器端的**访问控制（Access Control）和异常防御机制**是否严谨。

它的核心测试逻辑是“故意犯错”：通过 `try-catch` 语句块来模拟客户端的违规操作。如果在执行非法操作时，服务器成功阻击并抛出了异常（被 `catch` 捕获），说明服务器防御生效，测试**成功**；如果代码顺利执行完毕而没有报错，说明服务器存在漏洞放行了非法操作，测试**失败**。

**测试 1：未投票先看结果 (Deny fetching result before voting)**

- **行为：** 客户端正常获取了票据，但不执行投票步骤，直接调用 `fetchVotingResults()`。
- **预期：** 服务器由于该票据尚未激活投票状态，拒绝请求并抛出异常。

**测试 2：无票据直接投票 (Deny vote if ticket invalid)**

- **行为：** 客户端绕过 `getTicket()` 环节，直接使用未初始化的默认票据去调用 `vote(1)`。
- **预期：** 服务器在验证有效票据池时查无此票，拒绝投票并抛出异常。

**测试 3：非法选项拦截 (Deny illegal choice)**

- **行为：** 客户端拿到了合法票据，但尝试把票投给一个根本不存在的候选人（候选选项 `-1`）。
- **预期：** 服务器校验选项字典失败，拒绝计票并抛出异常。

**测试 4：重复投票拦截 (Deny double voting)**

- **行为：** 客户端拿到合法票据后，第一票成功投给选项 1，紧接着尝试用**同一张票据**再次投给选项 2。
- **预期：** 第一票正常放行；第二票时，服务器发现该票据已被标记为已使用，从而拒绝请求并抛出异常。



在实际运行中，全部测试都通过了！服务器也在日志中记录了对应的异常。

# GUI 投票系统

`VotingGUI.java` 使用 Java 的 swing GUI 架构实现了轻量级分布式投票客户端可视化界面。

- **服务端随动启动：** 在 `main` 方法中，GUI 启动前会专门开辟一个后台线程来异步执行 `Server.run()`，从而保证 RMI 服务端与 GUI 客户端在同一个进程中运行，且不会阻塞 GUI 主线程。
- **安全等待：** 主线程随后 `sleep` 1秒，确保 RMI 端口成功绑定后，再通过 `SwingUtilities.invokeLater` 渲染前端界面。

其中，GUI内部的逻辑交互，可以分为如下几个步骤：

- **创建选民 (Add Client)：** 点击按钮后，系统实例化一个 `Client` 对象，自动向服务端发起 RMI 调用获取选票（`getTicket()`），然后在左侧列表中新增一条带有 `[Not Voted]` 标记的记录。
- **动态获取选项：** 当用户在左侧点击一个未投票的客户端时，系统会触发 `refreshRightPanel()`。此时，GUI 会通过 RMI 实时调用 `client.getCandidateList()` 从服务端拉取最新的候选人名单，并动态填充到下拉框 `choiceComboBox` 中
- **执行投票 (Submit Vote)：** 用户选择候选人并提交后，客户端通过 `client.vote(choice)` 将票投出。随后，该节点的状态被标记为已投 (`hasVoted = true`)，左侧列表更新为 `[Voted]`。
- **实时查阅结果：** 投票完成后，右侧面板状态切换。系统自动调用 `client.fetchVotingResults()` 从服务端抓取所有选票的汇总数据，并利用简单的数学运算（当前票数/总票数）渲染出带有百分比的进度状条形图。



# Log 日志设计

在本项目中，所有必要的类（例如GUI、Server、Client、测试等）都包含了日志输出，以便在出现问题时可追溯。

- **控制台输出**：根据日志级别，`info` 使用标准输出 `System.out.print`，而 `error` 则被路由到了标准错误输出 `System.err.print`（在 IDE 控制台通常会以红色高亮显示，方便快速定位 Bug）。
- **文件持久化**：所有的日志都会被格式化为 `[时间] 级别 | 内容` 的标准格式，并持久化到 `GlobalConfiguration.LOG_FILE_PATH`（本项目是 `logs/voting.log`）中，方便运行并发测试后进行事后审计。

该日志的格式实现了一个 `formatMessage` 方法，模仿了 SLF4J 的 `{}` 占位符语法





# 总结与不足

## 过程中的假设与权衡

在并发控制方案上，系统选择了 `HashSet` + `HashMap` 配合 `ReentrantReadWriteLock` (读写锁)，而不是直接依赖 `ConcurrentHashMap` 等自带的并发集合。这是因为投票过程（验证票据和修改票数）必须作为一个不可分割的**原子事务**来执行。相比于并发集合只能保证单一操作的线程安全，手动加独占写锁能更可靠地将多个操作绑定在一起，彻底杜绝并发漏洞，同时代码的逻辑也更加清晰，便于后续维护。

## 开发与测试中观察到的问题及解决

在开发早期，直接启动 GUI 会导致主线程被服务端程序阻塞，进而引发界面卡死。

**解决方法**：将 `Server.run()` 放入独立的后台线程运行，并让主线程短暂休眠以等待 RMI 端口绑定完成，最后通过 `SwingUtilities.invokeLater` 异步渲染前端界面，成功解决了界面无响应的问题。

## 异常处理框架

项目实现了一套清晰的异常处理框架，自定义异常均继承自 `RuntimeException` 并以 `Client` 或 `Server` 为前缀，同时配合 `ExceptionName` 枚举类来统一规范异常的命名与信息。

另外，核心服务类 `CastVoteImpl` 继承了 `UnicastRemoteObject`。为了满足 Java RMI 框架处理网络不稳定和通信失败的标准强制要求，所有对外暴露的远程方法均按规范声明抛出了 `RemoteException`。

## 项目的不足之处

尽管系统在并发控制和核心访问逻辑上表现稳定，但距离真实的工业级应用仍存在以下局限性：

1. **数据缺乏持久化**：

   目前所有的票据和投票数据均驻留在内存中，服务器一旦停机数据即刻丢失。未来的改进方案是引入 MySQL 数据库（例如搭配 MyBatis 框架），并采用 Hash 索引，这样既能保证 $O(1)$ 的高效查询复杂度，又能实现数据的安全落地。

2. **客户端身份与公平性问题**：

   系统当前的访问控制逻辑是“认票不认人”。我们虽然能保证每一张 Ticket 只能投一次，但无法阻止同一个恶意 Client 疯狂调用 `getTicket()` 申请多张选票，这会破坏投票的公平性。

   理论上可以通过引入 UUID 来记录和限制单个 Client，但单纯的 UUID 极易被伪造。在现实的分布式选举系统中，解决这一问题需要结合更严格的身份校验机制（如 MAC 地址绑定、数字证书或账号鉴权）。受限于本次实验的范围，本项目的防御重点集中在“单张选票的防伪与防重复使用”上，暂未向更高维度的“用户物理实体防伪”做深入扩展。
